# Governance

## Model

pyverge uses a Benevolent Dictator For Life (BDFL) model.

The BDFL is the repository owner, JoHa-HQ. The BDFL has final authority over
technical direction, releases, and conflicts.

## Decisions

Every non-trivial change starts as an issue.

1. Proposal: describe the problem, constraints, and alternatives.
2. Discussion: allow reasonable time for maintainer and community feedback.
3. Decision: the BDFL accepts, rejects, or requests changes.
4. Implementation: accepted work follows the contribution and review process.
5. Release: changes ship through the documented release workflow.

Decisions are recorded in issues, pull requests, or the changelog. Private
discussions do not override public project decisions.

## Maintainers

Maintainers may:

- triage issues and pull requests
- review and merge contributions
- manage labels, milestones, and releases
- enforce the code of conduct

Maintainer access is granted by the BDFL based on sustained, constructive
contribution.

## Compatibility

Before 1.0:

- breaking changes are allowed
- breaking changes must be stated in the changelog and pull request
- public API changes should preserve a migration path where practical

From 1.0:

- semantic versioning applies to the public API
- breaking changes require a major release
- deprecated APIs remain for at least one minor release

## Releases

Release authority rests with the BDFL.

- releases are prepared from `main`
- changelog and versioning are generated by Commitizen
- release environments require reviewer approval
- release artifacts are published to PyPI and GitHub Releases

## Conflicts and conduct

Technical disagreements are resolved by evidence, compatibility, and the
documented project scope.

Conduct issues follow [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) and may be
reported privately to the maintainer.

## Changes to this document

Governance changes require a public issue and BDFL approval.
